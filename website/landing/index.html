An independent verdict on what an openEHR server implements

Point Veredictum at a running clinical data repository and it reports, with citations, which parts of the openEHR specification that server implements. It drives a machine-readable catalogue over the server's own wire, records every exchange, and computes verdicts as pure functions over the recording.

Veredictum is on 0.x and is not yet approved by the openEHR SEC. Version 1.0.0 will mark that approval.

Veredictum is medieval Latin for “truly spoken”, vere dictum, and it is the word that became the English verdict. The instrument runs the catalogue against a CDR and speaks a verdict on what it observed. The seal above is its mark.
What it does

Catalogue, run, verdict

Each stage is its own command and can be audited on its own. No stage hides what an earlier one recorded.

The catalogue

1896 test cases, one per behaviour, so a red row names one defect. Each is an Arazzo workflow over the released openEHR REST API, and each expectation quotes the sentence it comes from.

veredictum validate checks the catalogue. Zero findings is the only pass.

The run

Your statement names the capabilities you claim and your option arms. The instrument drives the selected cases and records every exchange as HAR.

veredictum test writes the recording and results.json, judged row by row.

The verdict

A verdict is a pure function of your statement, the recording and the catalogue: re-judging gives the same bytes on any machine, with no server.

veredictum test --rejudge reproduces the results from the recording alone.

One tool, two kinds of evidence

Functional conformance and measured performance

Both are recorded first and computed after, by one instrument.

InstrumentWhat it answersRecord
Functional
test		 Which capabilities does this server implement to the released specification, and which does it fail? results.json and the HAR recording it was judged from
Measured performance
perf		 Under the traffic a clinical front end sends, where does this deployment stop holding its latency budget, and how does latency move as load rises? perf-result.json with its HDR histograms, which perf-judge re-derives byte for byte
Comparison
perf-compare		 Is one deployment faster than another, or than the reference CDRs, by more than the noise between runs? Two records interleaved on one host and the ratios between them, judged against an A/A floor

Latency is measured from the instant a request was due under open-loop Poisson arrivals, so coordinated omission cannot hide a stall. The workload manifest lists the workloads.

Independence

No server grades its own homework

A vendor's own test suite is written by the same people, against the same reading of the specification, as the server it tests. When the two disagree, the suite usually gets adjusted.

Here the released openEHR specifications are the only authority, and the vendored text is never a suspect. Every expectation names its section, so only a better reading of the specification can refute it.

A red run is attributed before anything changes, to exactly one of three suspects, by comparing what the specification requires, what the catalogue expects and what the server did.

SuspectFix path
The server under test violates the specification The attribution is recorded with the reproduced exchange and the citation
The instrument misdrove the case or misjudged the response Fix the runner. Those rows were inconclusive, never failures
The catalogue expectation is wrong against the specification Fix the artifact, with a new cited source for the corrected expectation

The instrument is a suspect on every red row, ahead of the server. The first live triage attributed 7 of 7 diagnosed defects to the runner and none to the server under test. How the method works →

Quick start

Two products, one engine

The veredictum CLI installs from crates.io or a signed release binary; the container image is the web console over the same pinned CLI. The catalogue and specification oracle (over 300 MB) are read as paths into a clone of the repository.

Each release attaches x86_64 and aarch64 Linux binaries with a checksum, a CycloneDX SBOM and a Sigstore bundle. Installation, in full →

Veredictum

The independent conformance instrument for openEHR clinical data repositories. Licensed under Apache-2.0, with the NOTICE file. Vendored specification text and clinical models keep their upstream terms, recorded per tree.

To have a CDR graded, or to report a defect in this instrument, open an issue.
